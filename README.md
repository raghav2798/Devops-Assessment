# DevOps Assessment: Terraform + Database Reliability

`Internet → ALB → ECS/Fargate → RDS (PostgreSQL)` in Terraform (plan only), plus a local Postgres with migrations, seed data, an index, and backup/restore scripts.

## Layout

```
infra/modules/{network,ecs,rds}     infra/envs/{dev,prod}  (main, variables, backend.tf, terraform.tfvars)
db/migrations  db/seed              docker-compose.yml  scripts/{backup,restore}.sh
.github/workflows/terraform.yml
```

## Terraform

Requires Terraform >= 1.10. No AWS credentials needed.

```bash
cd infra/envs/dev        # or prod
terraform fmt -check -recursive ../../
terraform init -backend=false     # the S3 backend in backend.tf needs AWS access; skip it for review
terraform validate
terraform plan -refresh=false
```

`plan_only = true` in `terraform.tfvars` makes the AWS provider skip credential checks so `plan` works offline. Set it to `false` for a real deployment.

**Private RDS:** it sits in private subnets with `publicly_accessible = false`, and its security group has a single ingress rule: port 5432 from the ECS security group. ECS accepts traffic only from the ALB security group. The DB password is generated by RDS into Secrets Manager (`manage_master_user_password`) and injected into the task, so it is never in code or state.

| | dev | prod |
|---|---|---|
| State | `dev/terraform.tfstate` (own bucket) | `prod/terraform.tfstate` (own bucket) |
| RDS instance | `db.t4g.micro`, 20 GiB | `db.m6g.large`, 100 GiB, Multi-AZ |
| Backup retention | 1 day | 14 days |
| Deletion protection | false | true |
| Fargate | 256 CPU / 512 MiB x1 | 1024 CPU / 2048 MiB x2 |
| NAT gateways | 1 | 1 per AZ |

**CI:** the workflow runs on pull requests (`fmt`, `init`, `validate`, `plan` for dev and prod). The plan is visible in the job log and uploaded as an artifact.

## Local database

```bash
docker compose up -d --wait      # Postgres 16; migrations and seed run on first start
docker compose exec db psql -U app -d hotel -c "SELECT count(*) FROM hotel_bookings;"
```

Defaults: user `app`, password `app_password`, database `hotel` (override via `.env`, see `.env.example`).
Seed: 200 bookings, 5 orgs, 6 cities, 4 statuses, plus booking events.

### Index

```sql
CREATE INDEX idx_hotel_bookings_city_created_at
    ON hotel_bookings (city, created_at) INCLUDE (org_id, status, amount);
```

`city` is an equality filter so it goes first; `created_at` is the range filter so it goes second. `INCLUDE` adds the columns used by `GROUP BY` and `SUM`, allowing an index-only scan without reading the table. Check with `EXPLAIN ANALYZE` on the query. On only 200 rows the planner may still choose a sequential scan because the table is tiny.

## Backup and restore

```bash
./scripts/backup.sh     # backups/hotel_<UTC timestamp>.dump
./scripts/restore.sh    # restores the newest backup into a fresh database "hotel_restore"
```

**Verify the restore:** `restore.sh` prints row counts for the source and restored databases; they must match. You can also check manually:

```bash
docker compose exec db psql -U app -d hotel_restore -c "SELECT count(*), sum(amount) FROM hotel_bookings;"
docker compose exec db psql -U app -d hotel_restore -c "\d hotel_bookings"   # table and index are back
```

Reset everything with `docker compose down -v`.
